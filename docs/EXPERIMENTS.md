## E1 写入链路：小模型上的端到端表现（`research/personal-memory-write-path`）

**起因**：用 qwen2.5:3b 做冒烟测试时发现：提示词示例被写进了记忆、助手的建议被当成玩家事实、段位更新被漏掉、一次超时就让对话崩溃。前两类 bug 已在 main 上修复；其余的用 `e2e_v1` 量化。

**基线（dev p_support，16 题）**

| 系统 | E2EScore | 说明 |

**观察**：
- 16 道题的 dev 噪声很大：slots 在 R1 里最差，在 R2 里最好。以后只用 32 道题的 dev 做决定。

- 写入链路的每次 LLM 调用都限制输出长度（qwen2.5:3b 曾在结构化输出里卡住超过 600 秒）。

- 门槛：e2e 的 E2EScore 至少比基线高 0.03（improve），拒答率降幅不超过 0.05，过时率升幅不超过 0.05；检索 MemScore@3 降幅不超过 0.02（hold）。

**test 结果（e2e_v1 test，32 题 × 3 seed，按预登记只跑一次）**

**失败分析**（事后看 test，只用于解释，不用于调参）：负例误召回全都是同一种模式，"我喜欢什么颜色 / 运动" → "玩家最喜欢英雄是项羽"。只因为共享了"喜欢"这个谓词就被当成相关，而问的对象（颜色、运动）和记忆里的对象（英雄）根本不同。main 也有同样的误召回，候选只是在更多 seed 里恰好存下了"最喜欢英雄"这种说法。这是**检索层**的问题，不是写入链路本身。

**确实有的收获**：过时率减半（0.259 → 0.148）；写入更快、更稳（没有失控生成，用时 16.7 分钟对 26.8 分钟）；时间类问题从 0.533 升到 0.600。

**下一步**：
- 这次失败之后，e2e_v1 的 test 已经看过，不再用来做晋升决定。下一个候选改用 **e2e_v2 的 test**：它在这次分析**之前**就已封存（`eb8add4`），里面正好有"我喜欢什么电影 / 动物 / 喝什么茶"这类负例，可以公平地检验修复效果。
- 检索层修复方向：谓词类通用词（喜欢、讨厌、想、打算……）只算低权重，要求查询的"对象词"（颜色、运动）至少在字面或语义上命中一次，只在 dev 上开发。

## E3 P1：情景记忆、助手承诺、回忆模式

**第一版（e2e_v2 dev，seed 0）**：E2EScore 0.700（W1+W4 为 0.633）；情景 0.4 → 0.8，承诺 0 → 0.667，时间 → 1.0，但**更新题 1.0 → 0.2**。episode 记着当时的状态，问"我现在什么段位"时把旧值带了回来。

**修正**：
- episode 只回答关于某个时间或事件的问题（"那天、那次、上次、发生了什么"）；
- 没有版本链的变化轨迹，改用各时间点的 facts 和 episodes 按时间重建；
- "那天、发生"等表示时间指向的词加入停用词；
- 承诺不参与普通检索（它会挤掉相关事实），而是像待办清单一样固定放进聊天的 system prompt（`pending_promises`）。

**修正版 dev（2 个 seed 合并；最后一项承诺修改是在这组结果之后做的，这项修改只从普通检索里去掉 promise）**

## E4 检索：窄版偏好门槛（`research/personal-memory-consolidation`）

- **问题**：P1 在 e2e_v2 test 上的负例失败全部是同一种模式："我喜欢什么动物 / 喝什么茶" → "玩家最喜欢貂蝉 / 喜欢把字体调大"。
- **为什么 E2 失败**：E2 对**所有**查询都要求命中实词，否则需要余弦 ≥ 0.40。纯换说法、字面上毫无重合的正确匹配（"我为什么老是死" ↔ "被刺客切入"）也被挡住了。
- **E4 的规则**：只有当记忆和查询**仅**共享偏好谓词（喜欢、最喜欢、讨厌、最讨厌、爱）时，才要求余弦 ≥ 0.30；没有任何字面重合的记忆仍按原来的门槛。
- **阈值依据**：负例的余弦在 0.17–0.26；"我最讨厌别人说什么" ↔ "玩家讨厌有人说辅助没用"这个正例是 0.33；其余正例 ≥ 0.54。
- **dev 结果**：
  - retrieval_v2 dev：MemScore@3 0.872 → 0.936，Recall@3 保持 0.942，Abstain 0.731 → 0.923；`min_dense_alone` 在 0.25–0.45 之间结果完全相同。
  - e2e 回放（在已存的 dev 记忆上只重跑读取路径）：e2e_v2 dev 0.767 → 0.783（拒答 0.917 → 1.0）；e2e_v1 dev 0.609 → 0.609。
- **新工具**：`run_e2e --replay` 在已存的记忆上只重跑读取路径，不调用 LLM，读取层的实验几秒钟就能在 e2e 数据上评估。
- **状态**：写进 jina 的默认预设，和巩固（E5）一起作为下一个候选，判定用 e2e_v3 的封存 test。

## E5 巩固：段位 / 设备版本链

- **做法**：写入之后，一个确定性步骤识别封闭集合的属性值（段位档位、手机品牌；排除"冲王者"这类愿望句和"王者荣耀"这个游戏名），按时间把旧值依次串进版本链（`consolidate.py`）。LLM 已经建好的部分链会被正确拼接，不会覆盖。
- **c1（e2e_v3 dev，2 个 seed）**：巩固看起来有害（0.672 → 0.603，轨迹 0.5 → 0.167）。查下来发现是它暴露出的两个写入 bug：
  1. "玩家段位是铂金" → "玩家的段位是铂金"这种同义重述被当成新版本，链变成 白银→黄金→铂金→铂金，取前 3 个时丢掉了白银；
  2. 一段完全没提段位的对话里，模型写入了"玩家的段位是钻石"，而该玩家从没到过钻石。
- **修复**：几乎相同的 UPDATE 当作 NOOP；回忆轨迹时合并重复值；新写入的段位或设备值必须在对话原文（UPDATE 时也包括目标记忆）里出现过，否则拒绝写入。
- **c2（修复后，2 个 seed）**：

| | e2e_v3 dev | e2e_v2 dev |
|---|---|---|
| p1（含 E4、E5） | 0.724（轨迹 0.50，更新 0.857） | 0.733（轨迹 0.75，更新 0.70，过时率 0.10） |
| p1 + 巩固 | **0.759**（轨迹 0.667，更新 0.714） | **0.767**（轨迹 1.0，更新 0.80，过时率 0） |

- **预登记**（提交于 test 运行之前）：
  - 候选：`consolidate=True`（默认）+ E4 偏好门槛 + E5 写入修复（e2e 系统名 `p1+consolidate`，检索 `memory-default`）。
  - 基线：main @ `28832ed`（P1）的代码，在 worktree 中运行，e2e 系统名 `p1`。
  - 设置：**e2e_v3 test**（v3_mage、v3_jungle、v3_support，51 题，封存于 `b15eccc`），qwen2.5:3b，seed 0、1、2，结果合并。
  - 门槛：E2EScore 至少比基线高 0.03；拒答率降幅不超过 0.05；过时率升幅不超过 0.05；检索 MemScore@3 降幅不超过 0.02。

**test 结果（e2e_v3 test，51 题 × 3 seed，按预登记只跑一次）**

| 系统 | E2EScore | Answer@3 | 过时率 | 拒答率 | 轨迹 | 更新 | 事实 | 承诺 |
|---|---|---|---|---|---|---|---|---|
| main（P1） | 0.640 | 0.546 | 0.194 | 0.867 | 0.278 | 0.556 | 0.389 | 0.222 |
| 候选（巩固 + E4 + E5） | 0.667 | 0.528 | **0.139** | **1.000** | **0.056** | 0.556 | 0.444 | 0.333 |

Δ = +0.026，95% CI [−0.046, +0.105]，6 题变好、4 题变差。检索 hold 通过（0.892 → 0.912）。**门禁：NOT PROMOTABLE**（需要 +0.03），不合入。

**失败分析**（事后看 test，只用于解释）。巩固本来要改善轨迹，结果轨迹反而从 0.278 跌到 0.056。原因有三：
1. **段位粒度太粗**：识别器只认大段，钻石四 → 钻石一 → 星耀 这条链里，"钻石一"被当成"钻石四"的重复合并掉了。
2. **复合事实被整条作废**：像"玩家是大一新生，在武汉，段位黄金一"这样的复合事实，会因为段位变化被整条标为过时，连带把学校、城市也"忘"了。
3. **手机链经常断**：更早的手机记忆要么没抽到，要么没连进链（有一次模型把"一加13"写成了"加星手机"）。

dev 集没有发现这些问题：dev 玩家的段位变化都跨大段，而且事实比较短。

**确实有效的部分**：拒答 0.867 → 1.000（E4），过时率 0.194 → 0.139。但它们和巩固是打包预登记的，不能事后拆出来单独合入。

## E8 无损更新 + 按概念找回（`research/personal-memory-extraction`）

**诊断**（e2e_v5 test 在 P3 报告之后退役，改作 dev）。逐条检查 P3 的 19 个事实题失败：**每一个答案都曾经存进过记忆**（在事实里或 episode 里），并不是"没抽出来"。失败原因分三类：

1. **错误的更新 / 删除**把正确的事实变成了"已过时"：
   - 主语搞混："玩家老婆是银行柜员"作为 UPDATE 取代了"玩家是牙医，玩家在厦门开诊所，玩家主玩法师……"，职业、城市、位置一次全丢；
   - 有损复述："玩家常用赵云"取代了"玩家主玩打野，常用赵云"，位置丢了；
   - 无依据的删除：聊段位的那段对话里，把"玩家是学校篮球队的"删掉了。

   在所有存档的 run 里统计（246 次取代）：新内容只是旧内容子集的有 37 次，主语不一致的有 3 次。
2. **类别词压低覆盖率**："我是做什么工作的"分词成 ["工作", 概念职业]；"工作"这个类别词从不出现在"玩家是消防员"里，而且 idf 很高，覆盖率算出来 0.33，刚好低于门槛 0.34，事实明明在却召回不到。
3. **跑题的事实挡住了 episode**："我在哪个城市"通过"城市"标签匹配到"准备去成都玩"，于是不再去 episode 里找，而"来自重庆"只在 episode 里。

**做法**：
- 写入（`safe_updates`）：
  - DELETE 要求对话里提到被删的记忆；
  - 主语是别人的 UPDATE 改成 ADD；
  - 被取代的复合事实里，和新内容没有共同的值、概念或属性的分句，保留成独立的记忆。
- 读取：
  - `concept_cover`：带有所问概念标签的记忆，也算覆盖了类别词本身；
  - `concept_fallback`：找到的事实都不属于所问的概念时，也去 episode 里找；
  - 职业概念不再由"上班"触发（"在哪个城市上班"问的是地点）。
- 评测工具：LLM 回复缓存（`--llm-cache`）。两个系统遇到同样的请求时得到同样的回复，所以 A/B 的差别只来自系统本身的状态；重复运行也不再花 LLM 时间。

**读取侧配对回放**（8 组已存记忆，532 个题次，对比 P3 原来的读取路径）：+0.019，95% CI [+0.008, +0.032]，10 个变好 / 0 个变差。

**新的封存 test 集**：`e2e_v6`（`c259842`）。8 个 test 玩家，112 题（事实 56、负例 27、更新 13、轨迹 8、承诺 8），在开发之前由一个没看过系统代码的 agent 编写；在它上面跑任何系统之前就已提交。

## E9 按主语回忆（`research/personal-memory-subjects`）

**诊断**（e2e_v6 test 在 P4 报告之后退役，改作 dev）：近似负例的拒答率只有 0.358。失败的负例几乎都是**主语错了**：

- 问"我公公是做什么的"，返回"玩家婆婆是退休医生"；
- 问"我是什么学历"，返回"玩家的妹妹在读大二"。

**做法**（`subjects.py`）：
- 从问题里识别主语（亲属、伴侣、朋友、同事……），表亲（表 / 堂）和兄弟姐妹分开；所有指伴侣的词归为一组，因为同一个人婚前叫"女朋友"、婚后叫"老婆"。
- `subject_recall`：
  - 问某个人时，只考虑提到这个人的记忆，而且问题里指代这个人的词在覆盖率上算作已匹配（记忆里可能写的是"姐"或"妻子"）；

- `interleave_fallback`：概念兜底时事实和 episode 交错排列（修复 E8 里"男朋友是海员"那类回退）。
- "专业"是类别词，从专业词表的"值"里去掉。
