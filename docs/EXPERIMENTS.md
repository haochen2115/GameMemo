# 实验日志

每一轮实验记录假设、设置、结果和结论。dev 上的结果只用来做决定；进入 main 的依据是封存 test 上预登记的那一次运行（见 `docs/BRANCHING.md`）。

环境：4 核 CPU，本地 Ollama。写入模型 `qwen2.5:3b`（Q4_K_M），`temperature=0.1`，`seed=0`；向量模型 `jina-v2-base-zh`（fastembed）。

- **问题**：v1-hybrid（bge-small-zh）在 retrieval_v1 test 上拒答率 0.5，门禁不过。

- **结论**：预登记 v2-hybrid，test 0.892 vs v0 0.750，合入 main。详见 BENCHMARK.md。

## E1 写入链路：小模型上的端到端表现（`research/personal-memory-write-path`）

**起因**：用 qwen2.5:3b 做冒烟测试时发现：提示词示例被写进了记忆、助手的建议被当成玩家事实、段位更新被漏掉、一次超时就让对话崩溃。前两类 bug 已在 main 上修复；其余的用 `e2e_v1` 量化。

**基线（dev p_support，16 题）**

| 系统 | E2EScore | 说明 |
|---|---|---|
| v0-pipeline | 0.188 | 小模型下 JSON 解析全部失败，**一条记忆都没写入**；分数只来自负例（什么都不返回） |
| v2（main） | 0.500 | 9 条记忆；漏抽严重，没有时间信息 |

同时修了一个判分器 bug：答案关键词写成"6月28"时，"2026-06-28"会被判错。现在判分器会把 ISO 日期也展开成"M月D日"。

**R1（dev p_support，16 题，已用修正后的判分器重算）**

| 变体 | E2EScore |
|---|---|
| v2 | 0.500 |
| v2 + 只读玩家发言（W1） | **0.750** |
| v2-slots（W2） | 0.375 |
| v2-slots + 历史召回（W4） | 0.500 |
| v2-slots + W1 + W4 | 0.562 |

**R2（加入第二个 dev 玩家 p_mage2，共 32 题）**

| 变体 | E2EScore | Answer@3 | 过时率 | 时间类 |
|---|---|---|---|---|
| v2 | 0.531 | 0.423 | 0.250 | 0.200 |
| v2 + W1 | 0.562 | 0.462 | 0.125 | 0.400 |
| v2 + W1 + W4 | 0.688 | 0.615 | 0.125 | 0.400 |
| **v2-slots + W1 + W4** | **0.719** | **0.654** | **0.000** | 0.200 |

**观察**：
- 16 道题的 dev 噪声很大：slots 在 R1 里最差，在 R2 里最好。以后只用 32 道题的 dev 做决定。
- W1（只读玩家发言）和 W4（历史召回）在两轮里都是正向的。
- 仍然存在的失败：小模型把"前天"算错一天；没有事件日期的记忆答不了时间类问题；抽象问法检索不到。

**R3 改动**（对所有变体生效）：
- prompt 里直接给出"前天"的日期；
- 没有 `event_time` 的记忆显示"记于 YYYY-MM-DD"（双时态里的记录时间，相当于"你那天告诉我的"）；
- 写入链路的每次 LLM 调用都限制输出长度（qwen2.5:3b 曾在结构化输出里卡住超过 600 秒）。

**R3（32 题，3 个 seed）**

| 变体 | seed 0 | seed 1 | seed 2 | **均值** | 拒答率 |
|---|---|---|---|---|---|
| **ops + W1 + W4** | 0.750 | 0.656 | 0.656 | **0.687** | 1.000 / 1.000 / 1.000 |
| slots + W1 + W4 | 0.625 | 0.625 | 0.531 | 0.594 | 0.667 / 0.833 / 0.833 |
| ops + W1 + W4 + W5（逐句） | 0.625 | – | – | – | 1.000 |

时间类问题从 R2 的 0.2–0.4 升到 0.6–0.8，来自"前天"日期和"记于"两处改动。

**决定**：采用 ops + W1 + W4，放弃 W2（slots）和 W5（逐句抽取），至少在 3B 模型上如此。单次运行的波动约 ±0.1，所以 test 上基线和候选都取 3 个 seed 的均值。

**预登记**（提交于 test 运行之前）：
- 候选：`PersonalMemory` 默认开启 `player_only=True`、`history_recall=True`（e2e 系统名 `v2+po+history`，检索系统名 `memory-default`），见 `bench/candidate.json`。
- 基线：main @ `72bc605` 的真实代码（在 worktree 中用同一个 runner 跑），e2e 系统名 `v2`。
- 设置：`e2e_v1` test（p_tank、p_marksman2，32 题），qwen2.5:3b，seed 0、1、2，结果合并。
- 门槛：e2e 的 E2EScore 至少比基线高 0.03（improve），拒答率降幅不超过 0.05，过时率升幅不超过 0.05；检索 MemScore@3 降幅不超过 0.02（hold）。

**test 结果（e2e_v1 test，32 题 × 3 seed，按预登记只跑一次）**

| 系统 | E2EScore | Answer@3 | 过时率 | 拒答率 | 写入失败 | 用时 |
|---|---|---|---|---|---|---|
| v0-pipeline | 0.219 | 0.038 | 0.000 | 1.000 | 0 | 3.8 min |
| main（v2） | 0.583 | 0.538 | 0.259 | 0.778 | 1 段对话（失控生成超时） | 26.8 min |
| 候选 v2 + W1 + W4 | 0.594 | 0.577 | **0.148** | 0.667 | 0 | 16.7 min |

候选 − main：ΔE2EScore = +0.010，95% CI [−0.115, +0.135]（先按题目把 3 个 seed 取平均，再做配对 bootstrap），8 题变好、6 题变差。

**门禁：NOT PROMOTABLE**。主指标没达到 +0.03，拒答率下降 0.11，超过 0.05。候选**不进 main**。

**失败分析**（事后看 test，只用于解释，不用于调参）：负例误召回全都是同一种模式，"我喜欢什么颜色 / 运动" → "玩家最喜欢英雄是项羽"。只因为共享了"喜欢"这个谓词就被当成相关，而问的对象（颜色、运动）和记忆里的对象（英雄）根本不同。main 也有同样的误召回，候选只是在更多 seed 里恰好存下了"最喜欢英雄"这种说法。这是**检索层**的问题，不是写入链路本身。

**确实有的收获**：过时率减半（0.259 → 0.148）；写入更快、更稳（没有失控生成，用时 16.7 分钟对 26.8 分钟）；时间类问题从 0.533 升到 0.600。

**下一步**：
- 这次失败之后，e2e_v1 的 test 已经看过，不再用来做晋升决定。下一个候选改用 **e2e_v2 的 test**：它在这次分析**之前**就已封存（`eb8add4`），里面正好有"我喜欢什么电影 / 动物 / 喝什么茶"这类负例，可以公平地检验修复效果。
- 检索层修复方向：谓词类通用词（喜欢、讨厌、想、打算……）只算低权重，要求查询的"对象词"（颜色、运动）至少在字面或语义上命中一次，只在 dev 上开发。

## E2 检索：具体词门槛（针对共享谓词误召回）

- **假设**：只靠"喜欢、讨厌"这类通用谓词匹配时不算相关，除非向量相似度 ≥ `min_dense_alone`。
- **retrieval_v2 dev**（新增 8 道此类探针；test 部分有哈希校验，未改动）：MemScore@3 0.872 → 0.949，Recall@3 0.942 → 0.923，Abstain 0.731 → 1.000（`min_dense_alone=0.40`）。
- **e2e dev**（4 个玩家，seed 0；修掉"写入阶段候选检索也继承了门槛"的 bug 之后重跑）：

| e2e dev | 开门槛 | 不开 |
|---|---|---|
| e2e_v1 dev | 0.594 | 0.625 |
| e2e_v2 dev | 0.500 | 0.633 |

拒答率两边都是 1.0；开门槛后更新题和事实题的召回明显下降。
- **结论：放弃作为默认值**，保留为可选项。检索 dev 上的收益来自我针对这个失败模式补的探针；在真实 LLM 写出的记忆上，它挡住的正确召回比错误召回多。
- **不做的事**：W1+W4 候选已经在自己预登记的 test 上失败了。不拿同一个候选换一个 test 集重考（p-hacking）。下一个候选必须带来新的能力（P1）。

**噪声提醒**：同样的配置和 seed，e2e_v1 dev 在 R3 中得 0.750，这次得 0.625。CPU 上的 Ollama 即使固定 seed 也不完全确定，所以关键决定都要看多个 seed。
