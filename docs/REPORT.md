# 阶段报告：记忆系统到底该记什么（2026-10-08 ~ 10-09）

这一轮要回答的问题：GameMemo 继续做下去，怎样才能做出有影响力的结果？结论是先换评测，再换方向。下面每个数字都来自封存 test 集或预登记的实验，细节见 [EXPERIMENTS.md](EXPERIMENTS.md) 的 E11–E16。

## 一句话结论

**给小模型用的长期记忆，应该记原话，而不是让模型把对话改写成"事实"。** P0–P6b 一直在改进"改写成事实 → 在事实上检索"这条路，换成回答层评测后发现，这条路比"什么都不改写、直接检索原始记录"还差。改成原始记录为主后（P7、P8），在三个不同的封存 test 集上都明显超过原来的 main，而且写入不再调用 LLM。

## 1. 原来的评测看不到的问题（E11）

原来的 E2EScore 只看"检索到的前 3 条记忆里有没有答案关键词"，只能在记忆系统的不同版本之间比较。新的回答层评测（`bench/run_answer.py`）让模型真的回答每道题、再给回答判分，所以可以和两种不做记忆的做法放在一起比较：

| e2e_v10 test，128 题，每人 8 段对话 | AnswerScore |
|---|---|
| 不给任何上下文 | 0.250 |
| P6b（当时的 main） | 0.594 |
| 不写记忆，直接检索原始片段（`rag:5`） | 0.711 |
| 把全部聊天记录放进 prompt（约 1.2k 字） | **0.797** |

P6b 失分的原因：56% 是"写进了记忆但没检索到"，19% 是"根本没写进去"。把 P6b 的全部记忆都放进 prompt（比原始记录还长），仍然比原始记录低 0.16，说明**改写本身就丢信息**。

## 2. 记忆什么时候才有必要（E13）

用中性的填充对话把每个玩家的历史拉长：

| 每人的对话段数 | 全部记录放进 prompt | 原始片段检索 | P6b |
|---|---|---|---|
| 8 | **0.797** | 0.711 | 0.594 |
| 48 | 0.633 | **0.688** | 0.568 |
| 148（约 1.45 万 token） | 0.602 | **0.695** | 0.560 |

历史一长，全部放进 prompt 就崩了（3B 模型），耗时还是检索的 8 倍以上；检索几乎不受长度影响。所以**需要记忆，但要检索的是原话**。

## 3. 新系统（E14–E15）

`RawMemory`（`gamememo/personal/raw.py`）：
- 写入：每个"玩家一句 + 助手回复"原样保存，带时间，**不调用 LLM**；
- 助手的承诺：按规则从助手自己的话里找出，常驻 prompt；
- 读取：检索原始片段，按时间排列；问"段位 / 主玩英雄 / 手机怎么变的"时，把玩家说过的每个取值按时间列成一行（P8，取值用模式从原话里截出，不经过 LLM）。

| 封存 test 集 | 对比 | 结果 |
|---|---|---|
| e2e_v11（128 题） | P7 vs main P6b | 0.633 → **0.781**，+0.148 [+0.063, +0.234] |
| e2e_v11 + 140 段填充 | P7 vs 全部记录 | **0.750** vs 0.625，+0.125 [+0.047, +0.203] |
| e2e_v12（128 题） | P8 vs P7 | 0.672 → **0.727**，+0.055 [+0.016, +0.094]，7 好 / 0 差 |
| e2e_v12 | P8 vs main P6b | 0.547 → 0.727，+0.180 [+0.094, +0.266] |
| e2e_v12 + 140 段填充 | P8 / 全部记录 | **0.727**（不掉分） / 0.523 |

P6b 写一个 test 集要 867 次 LLM 调用、194 分钟；P7 / P8 不到 1 分钟、0 次调用。

## 4. 换成 7B 回答模型（E12）

| e2e_v10 test | 3B | 7B |
|---|---|---|
| 全部记录 | 0.797 | **0.852** |
| 原始片段检索 | 0.711 | 0.789 |
| P6b | 0.586 | 0.594 |
| P8 | 0.789 | 0.789 |
| P8（加 140 段填充） | — | 0.773 |
| 全部记录（加 140 段填充） | 0.602 | 0.695 |

大模型对"全部记录"帮助最大，对 P6b 几乎没有帮助（它的瓶颈在记忆的内容）。P8 − P6b 在 7B 下仍是 +0.195 [+0.109, +0.281]；7B 的"全部记录"到 148 段时同样崩（0.852 → 0.695，0 好 / 20 差），此时 P8 比它高 0.078 [+0.008, +0.148]。结论不依赖模型大小。

## 5. 没成功的和出过的错

- **P9**（"现在……"类问题的特殊处理）在 dev 上长历史 +0.030，但在封存的 e2e_v13 上只有 +0.016，没通过门禁。原因：P9 靠"现在 / 目前"这类词触发，旧 dev 集的 66 道更新题全是这种问法，新集换了说法后只有 11 / 40 触发。**dev 集的问法太单一，会让人高估这类改动。**
- **P10**（不看时态的"越新越准"提示）在 dev 上短 / 长历史 +0.025 / +0.044，在封存的 e2e_v14 上却是短历史 +0.055（显著）、长历史 +0.016（没到预登记的 +0.03 门槛），按规则未通过。
- **P9、P10 共同说明的问题：每个封存集只有 128 题，95% CI 宽约 ±0.04，分辨不出 dev 上 +0.03～+0.04 的改进。** 继续做小幅改进之前，要先把 test 集扩大到 256 题以上。
- 一次基线配置错误：P9 的预登记提交里，本应把 P8 固定为旧行为的修改没有生效，第一次比较实际是 P9 对 P9。已修正、重跑，并加了测试固定各系统的定义。
- 一次提交带着失败的测试（管道吞掉了退出码），已修正，之后每次都检查退出码。
- CPU 环境下多个任务共用一个 Ollama 会互相冲掉前缀缓存，长上下文时 llama-server 两次因内存不足被杀；改成单队列顺序执行，切换模型或跑长上下文前重启 Ollama。

## 6. 这个项目的影响力在哪里

1. **评测方法本身**是目前最有价值、最容易被别人用上的部分：回答层判分 + "全部记录 / 原始片段检索"两个朴素基线 + 用填充对话拉长历史 + 每个候选都在新的封存集上考。它直接暴露了"花了 6 个版本优化的方向是负收益"，这类问题在只和自己旧版本比较的评测里看不出来。整理成公开的中文陪伴型记忆基准（主语归属、AI 自己的承诺、多步轨迹、近似负例、长历史），并在上面跑 Mem0 / Zep / MemGPT 类系统，是最有可能产生外部影响的一步。
2. **"小模型 + 原话记忆"的工程结论**：写入零 LLM 调用、长历史不掉分、比改写式记忆高 0.15–0.2，对端侧和低成本部署的游戏陪伴很实用。
3. **仍然开放的问题**：非游戏属性的变化轨迹（工作、住处、家人）、不依赖关键词的"现状"判断、负例拒答，以及真实（而不是中性）的长历史噪声。

## 下一步

- **先提高评测功效**：已封存 e2e_v15（16 个玩家 / 256 题，`5d903d5`），留给下一个在 dev 上提升明显（≥ +0.05）的候选。
- P11（读取时用 LLM 列出状态）在 dev 上几乎无效，已放弃（E18）：非游戏轨迹的瓶颈是检索覆盖——同一件事的不同阶段用词不同。下一步可以试按"主语 + 类别"把同一件事的不同说法串起来（例如"老公 + 工作"），而不是只靠字面相似。
- **需要维护者决定**：P7 / P8 是否合入 main（需要开 PR）；P10 是否作为"短历史显著变好、长历史未达门槛"的例外合入（按规则默认不合入）。

- 新候选不再依赖问题里的表面词：例如对所有非变化类问题都提示"越往后越新"，或在检索结果里显式标出同一话题新旧说法的先后。e2e_v13 test 已退役，它更多样的问法作为 dev。
