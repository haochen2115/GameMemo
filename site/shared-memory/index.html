Shared Memory Is Harder多租户客服智能体的共享记忆：经验要迁移，客户不能串

GameMemo 项目 · 2026 年 8 月提出，10 月完成 COMMONS-1 模型实验

代码与文档 实验记录 COMMONS 规范 威胁模型
一句话：个人记忆只有一个目标——把这个用户记准。共享记忆有两个互相冲突的目标：让早先客户的成功经验帮到新客户，同时绝不把某个客户的具体信息带给另一个客户。问题不在容量，而在粒度：太具体会泄露上一个客户，太抽象又教不会下一个客户。

为什么共享记忆不同

目标希望的行为失败方式
跨租户迁移把成功的处理流程用到新租户上学不到东西，重复犯错
租户隔离每个客户的具体信息只留在本地实例泄露：另一个客户的名字、订单、地址出现在当前上下文
适用范围正确学到的规则只在条件成立时使用伪泛化：某个客户的特例被当成通用规则

访问控制标签解决不了这两种污染：它能隐藏一行数据，却挡不住摘要模型把这行内容写进全局可读的摘要。所以 QUORUM 约束的是写入路径，而不只是读取路径。

QUORUM：两层记忆 + 法定人数晋升

租户平面                                 共享平面
─────────────────────────────           ─────────────────────────────
原始交互                                 条件化的处理规则
私有事实                                 汇总的成功 / 失败次数
租户本地的结果               ───────▶    加盐的支持者令牌
指向共享规则的指针                       不透明的证据哈希

原始交互从不进入共享平面。共享平面只接收结构化的候选：任务、条件、泛化后的动作、结果。一条候选晋升为共享规则，必须同时满足：

  1. 候选里没有声明过的私有事实，也没有明显的标识符；
  2. 有足够多不同的租户独立支持它（同一租户重复多次不算）；
  3. 汇总成功率达到阈值；
  4. 失败次数低于上限；
  5. 检索时，规则的条件和新租户的情境匹配。

COMMONS-1：第一次模型实验

一个电商平台的客服 AI 为很多店铺服务。不看代码的作者编写了平台的 8 个内部处理流程（每个有一个编造的操作名，如「资金回流核单」，模型不可能凭常识猜到）、4 个店铺专属约定（如 VIP 会员退款由店铺余额先行垫付），以及全部对话。12 个训练店铺依次产生 29 条处理记录（8 个流程分别被 5/4/3/3/2/2/1/1 家店铺成功处理过）；8 个留出店铺的顾客带着同样的问题来求助（test 48 条）。顾客姓名、订单号、手机号、地址是生成的金丝雀，判分全部是确定性的；假设在跑 test 之前预登记。

发现

  • 风险在上下文，回复层只是冰山一角。原始共享池每一次检索都把别家顾客的姓名、订单号、手机号交给模型；3B 没有照抄，换成 7B 就把一位训练顾客的手机号写给了三家不同店铺的新顾客。
  • LLM 去隐私挡得住个人信息，挡不住伪泛化。摘要模型不知道"玻璃器皿补发并加赠防震收纳盒""VIP 先行垫付"只是某一家店铺的约定，把它写成了普遍经验；7B 在 25% 的相关求助里照做了。
  • QUORUM 在两个模型上都做到了结构性隔离（泄露、伪泛化、上下文暴露都是 0），代价是迁移：只有 1–2 家用过的流程按设计不共享，抽象规则也不如具体示例好用（支持 ≥3 家的流程上 0.75 vs 1.00）。
  • 最有效的迁移形式最难安全共享。给规则附上用占位符脱敏的处理示例，3B 下增益从 0.229 升到 0.542（k=2），却出现了 2 次泄露：示例里的"金女士"不是声明过的字段，模型用它称呼了另一家店铺的新顾客。
